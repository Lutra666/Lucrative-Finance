# 移除强制改密与登录锁定 — 设计文档

- 日期：2026-09-20
- 项目：Lutra财务系统
- 目标版本：1.0.9 → 1.0.10
- 状态：已批准，待实现

## 1. 背景

本机安装的 v1.0.9 桌面版在使用中遇到两处阻塞：

1. **强制改密弹窗无法关闭**。只要 `admin` 账号的密码仍是默认值，登录后 `frontend/src/app.js` 会弹出一个 `closable={false}`、`maskClosable={false}`、`keyboard={false}` 且隐藏取消按钮的 Modal，不完成改密就无法进入系统。
2. **登录失败锁定**。连续 5 次密码错误后账号被锁定 15 分钟。实际排查过程中该锁定已被触发一次，进一步阻碍了测试。

此外，需要将修复后的版本发布到 GitHub。

## 2. 目标与非目标

### 目标

- 默认密码登录后可正常使用系统，仅保留不拦人的提示
- 彻底移除登录失败锁定机制
- 让**已安装的程序**立即体现上述改动，无需重新安装
- 源码同步修改并准备发布 v1.0.10

### 非目标

- 不重新打包 NSIS 安装器（`npm run dist:win` 成本高，本次不需要）
- 不改动密码校验、JWT 签发与鉴权逻辑
- 不引入新的密码强度策略

## 3. 已确认的设计决策

| 决策点 | 结论 |
|---|---|
| 强制改密的替代行为 | 保留弹窗，但改为可关闭；不做成通知或横幅 |
| 登录提示去重 | 只保留弹窗，删除 `Login.js` 中的 `message.warning` |
| 弹窗重现策略 | 用户关闭后清除 localStorage 标记，本次登录内不再出现 |
| 锁定功能的处理 | 彻底删除代码，而非用配置关闭 |
| 已安装程序的同步方式 | 后端直接编辑；前端重新构建后整体替换 |
| 版本号 | 1.0.9 → 1.0.10 |

## 4. 详细改动清单

### 4.1 后端 — `backend/src/routes/auth.js`

**删除：**

- `lockMaxAttempts`、`lockMinutes` 常量（约 L9-10）
- MySQL 侧内存锁相关：`mysqlLockMap`、`getMysqlLockState`、`recordMysqlLoginFailure`、`clearMysqlLock`（约 L16-53）
- 登录路由中 4 处 `res.status(423)` 分支（约 L82-87、L96-103、L107-112、L118-125）
- 2 处 `recordLoginFailure` / `recordMysqlLoginFailure` 调用
- 成功登录时的 `clearMysqlLock(username)` 调用（约 L146）—— 该函数已被删除，调用点必须同步移除，否则会抛 `ReferenceError`

**保留：**

- 密码校验（`bcrypt.compare` / `store.verifyUserPassword`）
- JWT 签发与 `touchLastLogin`
- 登录失败时统一返回 `401 用户名或密码错误`

### 4.2 后端 — `backend/src/data/mockStore.js`

**删除：**

- `getUserLockState`、`recordLoginFailure` 两个函数及其在模块导出中的条目

**保留：**

- `normalizeUsers` 中的 `failedLoginAttempts` 与 `lockedUntil` 字段。
  理由：`normalizeState` 在每次启动时都会执行，移除字段会导致已有数据被静默丢弃。这两个字段今后不再被读写，属于无害残留。**改功能与改数据 schema 应分开处理**，混在一起会让回滚变复杂。

### 4.3 后端 — `backend/.env.example`

删除 `ACCOUNT_LOCK_MAX_ATTEMPTS` 与 `ACCOUNT_LOCK_MINUTES` 两行配置及其注释。

### 4.4 前端 — `frontend/src/app.js`

Modal（约 L351-360）修改：

| 原属性 | 改为 |
|---|---|
| `closable={false}` | 删除（恢复默认 `true`） |
| `maskClosable={false}` | 删除 |
| `keyboard={false}` | 删除 |
| `cancelButtonProps={{ style: { display: 'none' } }}` | 删除 |
| `title="首次登录请先修改密码"` | `title="当前正在使用默认密码"` |

**新增 `onCancel` 处理**：清除 `localStorage` 中的 `requirePasswordChange` 标记，并将 `requirePasswordChange` state 置为 `false`，使弹窗关闭且本次登录内不再重现。

`onOk` 与内部表单**原样保留** —— 这是当前界面中唯一的改密入口，不能丢失。

### 4.5 前端 — `frontend/src/pages/Login.js`

删除登录成功后的 `message.warning('检测到默认密码，需先完成改密后才能继续使用')`（约 L18-20）。该文案中的"需先完成改密后才能继续使用"在改动后已不成立，且与弹窗信息重复。

若删除后 `message` 在本文件中不再被使用，一并移除其 import。

### 4.6 前端 — `frontend/src/services/api.js`

删除 `status === 423` 分支（L27-28）。后端不再返回 423，该分支成为死代码。
注意：`message` 在同文件的 401/403（L23）与 429（L29）分支中仍在使用，**import 必须保留**。

### 4.7 前端 — `frontend/src/pages/Data.js`

删除 L202 中"连续密码错误达到阈值后，账号会临时锁定。"这句说明文案。

### 4.8 文档 — `readme.md`

- 从安全特性列表（L151）删除"登录失败锁定（次数和时长可配置）"
- 版本历史表新增 1.0.10 条目

文档不应宣称已经不存在的能力。

### 4.9 测试 — `backend/src/__tests__/auth.test.js`

**必须处理**：L77-91 存在一条断言锁定行为的测试：

```js
describe('POST /api/auth/login — lockout', () => {
  it('locks account after too many failed attempts', async () => {
    // ...连续 5 次错误密码
    expect(res.status).toBe(423);
    expect(res.body.error).toContain('锁定');
  });
});
```

移除锁定机制后该断言必然失败。

**处理方式：反转测试，而非删除。** 改为断言"多次失败后仍然返回 401，不会被锁定"，将新的预期行为固化下来，保留对登录失败路径的覆盖：

```js
describe('POST /api/auth/login — 无锁定', () => {
  it('连续多次失败仍返回 401，不锁定账号', async () => {
    // ...连续 5 次以上错误密码
    expect(res.status).toBe(401);
  });
});
```

另注：根目录 `CLAUDE.md` 中"Jest is configured, but no actual test files exist yet"的说法与现状不符（实际存在 `auth.test.js` 与 `orderHelpers.test.js`）。此为既有文档陈旧问题，**不在本次改动范围内**，仅作记录。

当时的安装目录：`%LOCALAPPDATA%\Programs\Aolong Finance System\resources\`（历史路径，保留原名以便定位旧版安装）。

### 后端 — 直接编辑

`resources/backend/src/routes/auth.js` 与 `resources/backend/src/data/mockStore.js` 是**未混淆的明文 JS**（实测与源码逐字节一致），可直接应用与源码相同的修改。

### 前端 — 重新构建后整体替换

两条路径均已验证：

| 方案 | 可行性 | 问题 |
|---|---|---|
| 直接修补压缩代码 | 目标串已精确定位：`title:"…",closable:!1,maskClosable:!1,keyboard:!1,…` | 新增 `onCancel` 属于**注入新逻辑**，需手工向压缩代码写入 `onCancel:()=>{localStorage.removeItem("requirePasswordChange"),d(!1)}`，易出错 |
| 重新构建后替换 | `frontend/node_modules` 齐备（924 包）；实测源码 `frontend/build` 与安装目录 build **逐字节一致**，说明当前源码即构建安装包时所用 | 需实测构建能否跑通 |

**选定重新构建。** 由于构建产物与源码严格对应，重建可安全替换，且 `onCancel` 由源码自然生成。

### 待验证风险

**应对：先单独执行一次前端构建以验证可行性，再决定是否采用重建方案。若构建失败，退回压缩代码修补方案。**
